---
title: '独立开发做媒体资产，别只盯着R2和S3的存储成本'
date: '2026-09-29'
---

> 做独立开发时，无论挂的是 Cloudflare R2 还是 S3，很多人都会把注意力放在免费额度、存储成本和免运维上，却很容易忽略一个更直接影响用户体验的问题：**媒体资产本身到底有多大，以及用户实际加载起来是什么体感。**

用户上传的原图动辄五六兆，录音文件更是几十兆的原声。如果这些文件不做任何处理，直接原样丢进对象存储，即使存储费用再便宜，弱网环境下的首屏加载依然会明显变慢；音频文件过大时，用户拖动进度条也更容易遇到缓冲和卡顿。

所以，在资源有限、又不想把基础设施搞得太复杂的情况下，我更推荐在资产入库之前增加一条轻量的压制流水线。

核心思路很简单：**用户上传原始文件，服务端先完成压制和格式转换，再把最终成品写入对象存储。**

## 图片：优先使用 WebP

图片格式优先考虑 WebP。

这两年 AVIF 的讨论度确实很高，但真正落地到独立开发项目时，还需要考虑编码耗时、设备性能以及兼容性。AVIF 的 CPU 编码成本相对较高，部分老设备或 WebView 在解码时也可能占用更多性能。

相比之下，WebP 在移动端和现代浏览器中的支持已经非常成熟，实际项目里更容易做到“压完就用”。

如果使用 Node.js 的 `sharp` 进行处理，可以把 `quality` 设置在 **75～80** 左右。具体效果会受到原图内容影响，但在很多照片场景下，体积可以直接压缩掉 **70% 以上**，肉眼通常很难感受到明显的画质损失。

原本一张几兆的手机照片，经过处理后可以直接收敛到两三百 KB。

这时候用户实际感受到的就不是“对象存储便宜了”，而是页面打开以后图片更快出现了。

## 音频：语音场景优先使用 AAC + m4a

音频则可以优先考虑标准 AAC，并封装成 `m4a`。

做语音、播客或者 AI 配音类产品时，很多人习惯直接保存 MP3，或者把浏览器录制出来的 WebM 原样存下来。

Opus 的压缩效率确实很好，但实际做面向普通用户的产品时，还需要考虑终端兼容性。尤其是在 iOS Safari 以及苹果生态中的部分嵌入式浏览器环境里，可能会遇到解码异常、进度条无法正常拖动等兼容性问题。

AAC 的优势在于生态成熟，苹果设备拥有原生硬件解码支持，功耗相对较低，同时在 Android 和 PC 浏览器环境中也有很好的兼容性。

如果主要是语音场景，通常没必要保留立体声。直接转换成**单声道**，再把码率控制在 **48k～64k**，已经能够满足大多数语音、播客和 AI 配音场景。

按照 **64k** 的码率计算，一分钟音频大约只有几百 KB，实际文件大小通常可以控制在 **不到 0.5 MB** 的量级。

相比几十 MB 的原始录音，这种差距对实际加载体验非常明显。

## 实现并不复杂，关键是把它放进上传链路

技术实现其实不需要搞得很重。

图片在 Node.js 服务里调用 `sharp` 进行压缩，音频则可以在后台交给 FFmpeg 做格式转换，例如：

```bash
ffmpeg -i input.wav -c:a aac -b:a 64k -ac 1 output.m4a
```

真正值得做的不是单独写一个压缩脚本，而是**把这两个步骤固化到文件上传管道里**。

用户上传原始图片或音频之后，服务端自动完成压缩、转码和格式转换，最终只把处理后的成品写入对象存储。

这样一来，R2、S3 里长期保存的就不再是几 MB 甚至几十 MB 的原始媒体文件，而是已经适合 Web 端交付的资源。

当然，如果产品后续还需要支持原文件下载、重新编辑等场景，原始文件仍然可以单独归档；这里针对的是面向网页访问的媒体成品。

这套方案真正节省的不只是存储空间。

**文件变小以后，CDN 分发成本、网络传输时间以及用户等待时间都会一起下降。**

对于独立开发者来说，基础设施不一定要做得多复杂。很多时候，只是在文件进入对象存储之前增加一个几十行代码就能完成的处理环节，就能同时解决成本和体验两个问题。

最终的目标其实很简单：**用户上传什么是用户的事，网站最终交付给用户的资源，应该是已经为 Web 场景优化过的资源。**
