本文根据《SEO实战密码》中与快速诊断、网站结构、页面优化相关的审查清单整理，并对照 [Google Search Central](https://developers.google.com/search/docs) 与 [Bing Webmaster Guidelines](https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a) 的公开说明做了必要校正。清单里的检查维度大多仍有用，但书中不少「合格线」是当时的经验数字，不能当成搜索引擎的硬指标。

下面按优先级写：先看大问题，再修会阻断抓取和分散信号的结构问题，最后落到单页。每项都给出检查什么、怎么查、如何判断、怎么改。

## 建议的执行顺序

1. 用 Search Console、Bing Webmaster Tools 看收录与抓取，先定位大面积异常，而不是先抠标题字数。
2. 排除会让爬虫进不去或看见错内容的问题：错误的 robots、登录墙、不可抓取的链接、异常跳转。
3. 把同一内容的多个网址收拢到规范 URL，处理复制内容和软 404。
4. 理清 URL、内链可达性和真实的 404。
5. 再逐页检查标题、正文、标题层级、图片替代文字和描述。

结构是否健康、重要页面是否能被发现和理解，通常比单页上的「优化技巧」更先决定审查效果。公开文档没有给出「页面优化占算法 20%～30%」这类比例，不必用这个数字做决策。

## 一、先诊断收录与抓取

### 看的是覆盖原因，不是一个及格百分比

要检查的是：你希望出现在搜索结果里的 URL，实际被编入索引了多少，以及没编入的原因。

怎么查：先从 CMS 或数据库统计「应该被索引」的页面，不要把筛选页、打印页、参数组合页全都算进分母。再到 Google Search Console 的网页报告、Bing 的索引/抓取报告里，对照「已编入索引」和各类排除原因。站点内搜索指令只能作粗略参考，不能当精确计数。

如何判断：公开文档没有「收录率达到 60% 就算合格、落到 20%～30% 就说明结构一定有大问题」的标准。更有诊断价值的是：重要产品页或文章是否大量「已发现但未编入索引」、被 robots 误挡、重复而不规范、软 404，或抓取到了却质量信号不足。小站点如果核心页都在索引里，即使总体比例不高也不必先焦虑数字。

怎么改：按排除原因逐项修，而不是先追求把比例做上去。优先保证最终有搜索需求的页面能被发现、被选为规范版本；减少排序页、筛选页、多入口复制页去挤占抓取和索引。

### 用站长工具做体检，但不要给抓取量设最低门槛

要检查的是：安全与人工措施通知、抓取统计和抓取错误、覆盖情况、重复标题或描述、核心查询是否跑偏、网站体验与明显性能问题。

怎么查：把站点加到 [Google Search Console](https://search.google.com/search-console) 和 [Bing Webmaster Tools](https://www.bing.com/webmasters)，看抓取统计、网页报告和体验报告。需要判断「用户看到的」和「爬虫看到的」是否一致时，用 URL 检查或等价的抓取测试。

如何判断：出现大量 404、服务器错误、重复标题、模板噪声词（如评论区的 Reply/says）占据页面主题，都值得处理。但「大中型网站每天必须被抓取几万个页面」并不是官方最低标准。Google 对[抓取预算](https://developers.google.com/search/docs/crawling-indexing/large-site-managing-crawl-budget)的说明是：它由服务器承受能力和抓取需求共同决定，主要影响页面很多、更新很快的大站；需求来自内容更新、受欢迎程度和 URL 库存是否干净。抓取量低，更应先问服务器是否报错过慢、是否在浪费预算抓重复 URL，而不是先对外链数量下结论。

怎么改：先修 5xx/超时、软 404 和重复 URL 库存；再加强重要页面的内链和sitemap。抓取预算通常不是中小站点的第一优先级。

## 二、排除抓取障碍，并正确控制索引

### 仍要避开的障碍，以及需要改口径的「JS 导航陷阱」

要检查的是：重要内容是否只能在登录后看到、URL 是否携带 Session ID、是否还在用框架集、是否用无法被解析的方式做跳转，以及导航和正文链接是不是可抓取的 HTML 链接。

怎么查：看首页和关键模板的源代码，确认链接是带 `href` 的 `<a>`。用 Search Console 的 URL 检查对比原始 HTML 和渲染后的 HTML。检查 URL 里是否出现 sid、session 一类参数。

如何判断：登录墙后的内容、强制用户授权才能出正文、Session ID 把同一页变成无数 URL，这些问题今天依然成立。Flash 整站、Frame 套页在现代站点已少见，一旦还有，应改成普通 HTML。

关于 JavaScript：Google 可以在渲染阶段执行 JS，并用 JS 注入到 DOM 里的标准 `<a href>` 发现链接，详见 [JavaScript SEO 基础](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics) 和 [可抓取链接说明](https://developers.google.com/search/docs/crawling-indexing/links-crawlable)。因此，「导航是 JS 生成的就一定是蜘蛛陷阱」已经不准确。仍不可靠的是：只有 `onclick`、没有 `href` 的假链接，或只用 `#/page` 这类片段来表示不同页面。Bing 同样建议不要把关键内容只藏在客户端渲染里，必要时提供完整 HTML。最稳妥的做法，是让重要链接在渲染结果里仍是标准锚点，并抽查渲染 HTML。

怎么改：会员区如果本来就不该出现在搜索结果中，就不要指望爬虫登录。Session 放到 cookie，不要写进 URL。关键导航和正文链接改成可抓取的 `<a href>`；单页应用用 History API 给出可单独访问的 URL。

### 跳转：优先用含义正确的 HTTP 重定向，而不是「全部改 301」

要检查的是：页面之间如何跳转，尤其是换域名、去掉 www、HTTP 升 HTTPS、以及废弃 URL。

怎么查：用命令或开发者工具看响应头状态码，不要只看浏览器地址栏。

如何判断：永久搬家应使用 [301 或 308](https://developers.google.com/search/docs/crawling-indexing/301-redirects)；临时搬家用 302、303 或 307。Google 会跟随这些跳转，但对永久与临时的规范信号强弱不同，302 并不是「一律无效」或「一律是陷阱」。服务器端跳转最稳妥。`meta refresh` 立即跳转会被当成永久跳转，带延迟则偏临时；JavaScript `location` 跳转只应在无法做服务器跳转时才用，因为渲染失败时搜索引擎可能看不到它。不要把已删除页面 301 到首页，以免造成软 404。

怎么改：能在服务器配置的，就用正确语义的 HTTP 重定向，并尽量指向最终地址、少做跳转链。废弃内容返回 404 或 410，或 301 到真正对应的新页面。

### robots.txt 和 meta robots 各管一件事

要检查的是：`/robots.txt` 有没有误禁应收录的目录，有没有声明 Sitemap；需要不出现在结果里的页面，是不是用了正确的 `noindex`。

怎么查：直接打开 `https://你的域名/robots.txt`，再用 Search Console / Bing 的 robots 测试。查看目标页 `<head>` 或 HTTP 头里的 robots 规则。

如何判断：robots.txt 阻止的是抓取，不保证结果里完全看不到该 URL；要避免编入索引，应允许抓取并用 `noindex`（或密码保护等更强方式）。正常页面不必写 `index,follow`，那是默认行为。也不要把 `nofollow` 或「少放内链」当成禁收录手段。

怎么改：需要屏蔽的打印页、无意义筛选页，逐条写 `Disallow`，改完用测试工具验证再上线。确定要排除的页面加 `noindex`；如果还希望链接被跟踪，不要顺手加上 `nofollow`。文件缺失时，应避免对 `/robots.txt` 返回带错误正文的 200 页面。

### 不要再用 nofollow 在站内「调权」

要检查的是：模板里的 `rel` 是否被用在不该用的地方，尤其是分类、产品、重要内容页。

怎么查：检查全站页头、页脚、导航和正文链接的 `rel` 属性。

如何判断：对付费链接、广告、用户评论里的外链，应使用 [sponsored、ugc 或 nofollow](https://developers.google.com/search/docs/crawling-indexing/qualify-outbound-links)。自 2019 年起，Google 把这些属性当作[提示而非硬指令](https://developers.google.com/search/blog/2019/09/evolving-nofollow-new-ways-to-identify)。用 nofollow 给站内「隐私政策、登录页」调权、或靠它把权重挤到某一条首页锚文本上，并不是官方推荐做法；要减少某些内页被抓取，更合适的是 robots.txt，要避免索引则用 `noindex`。页脚堆积完全匹配关键词链接仍然应当避免，这是可用性问题和过度优化风险，不是靠 nofollow 就能理顺的。

怎么改：让首页和主导航直接链向真正重要的栏目与内容；登录、购物车等对搜索无意义的页面可以不作为收录目标，但不要把站内调权当成常规动作。

## 三、把同一内容收拢到一个网址

### 规范化：选定一个 URL，用 301 和 canonical 一起收口

要检查的是：同一内容是否能通过带/不带 www、index.html、尾斜杠、http/https、跟踪参数、参数顺序不同等多种网址打开。

怎么查：把这些变体逐个访问，看状态码和最终落地页。检查内链、sitemap 用的是不是同一套规范 URL。Search Console 里曾经的「首选域」设置已经不再作为主要手段，不要再指望后台点一下就能完成规范化。

如何判断：应有一个明确的规范网址。其他变体用永久重定向指向它；HTML 里的 [`rel="canonical"`](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls) 是强烈提示，不是可强制覆盖一切的指令，建议使用绝对地址，并与内链、sitemap 保持一致。完成合并需要时间，公开文档没有「Google 固定要 1 到 3 个月」的承诺。

怎么改：CMS 只输出规范 URL；内链和 XML 地图只用这一套；在服务器上把变体 301 或 308 过来；排序、筛选等近似页用 canonical 指向主版本。多域名时选定主域，其余永久重定向过去。

### 复制内容：先减少可抓取的重复版本

要检查的是：打印版、排序/显示方式页、时间存档、Session 页、地区名替换的近复制页，以及任意加字符仍返回 200 的地址。

怎么查：在 Search Console 里看重复标题、重复描述和「重复网页，用户未选定规范网页」。从正文中摘一句加引号搜索，看是否打出多个本域结果。

如何判断：一篇实质内容应对应一个可被索引的 URL。可以存在供用户使用的复制视图，但不应让爬虫把它们都当成独立结果。正文过短、几乎全是导航和页脚，也容易变成近似重复。

怎么改：先按上一节做规范化。需要保留但不想被索引的版本，用 `noindex` 或合理的 robots 规则处理。跨站转载时应标明出处并链向原页；发现被大量复制，再考虑联系对方或走官方举报渠道。不要把「零外链」或「转载没声明」以外的问题，都归到这一项里一次性处理。

## 四、URL、内链、地图和 404

### URL 设计服务人和爬虫，不必神化「必须静态化」

要检查的是：URL 是否稳定、可读、参数是否失控、大小写是否混用、是否把 Session 写进路径。

怎么查：抽查栏目页、文章页、筛选页的地址。

如何判断：短、描述清楚、全小写、单词用短横线分隔，对用户和分享都更友好。参数并非一律不能用，但无意义的长参数组合会制造重复 URL。Google 可以抓取动态 URL，「没做成伪静态就无法做好 SEO」并不成立；仍建议减少不必要参数，并保证同一内容只有一个规范地址。Linux 上大小写不同会变成不同资源，混用容易 404。

怎么改：能伪静态就仔细测试重写规则；短做不到，就先砍参数、统一大小写和尾斜杠，并配好重定向。

### 内链要让重要页可到达，而不是满足点击次数公式

要检查的是：重要栏目和内容是否能从首页或主导航到达；分类是否孤岛；分页是否把产品页埋得过深；导航锚文本是否清楚，有没有在页脚堆关键词。

怎么查：从首页点到目标页，看路径是否合理。用站长工具或爬虫图看孤立页。抽查导航和正文锚文本。

如何判断：「所有页面离首页不超过 4 到 5 次点击」是常见的架构经验，不是官方硬门槛。真正要避免的是：重要页只能靠站外链接进入、分页没有可达的 HTML 链接、分类互不连通。导航锚文本应清楚描述目标页，可自然变化，不必为了「完全匹配」在页脚重复堆砌。相关推荐有助于发现，但应指向真实相关的页面。

怎么改：首页和主导航给重点栏目直链；大分类需要时再做细分或分页，分页使用可抓取的 URL。给旧内容保留入口。不要把「再补一点外链」当成结构问题的第一解法，先把内链补上。

### 网站地图是辅助，不是结构的替代

要检查的是：是否有面向用户的 HTML 地图（可选但有用），以及是否有已提交的 XML Sitemap。

怎么查：打开 sitemap.xml，确认 robots.txt 中的 `Sitemap:` 行，并在 Search Console 与 Bing Webmaster Tools 中提交。

如何判断：XML 地图应只列出你想被索引的规范 URL。Google 现行限制是单个文件不超过 [50,000 条 URL 或未压缩 50MB](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)，超出就拆分并用索引文件。`lastmod` 只有在真实反映重要更新时才有用；Google 公开表示不使用 `changefreq` 和 `priority`。地图不能弥补导航无法到达的结构缺陷。

怎么改：生成并提交仅含规范 URL 的地图，保持更新；不要指望靠地图「救」那些既无内链、又质量不佳的页面。

### 404 必须是真 404，不要指回首页冒充正常页

要检查的是：不存在的地址返回什么状态码，自定义错误页是否可用。

怎么查：访问一个肯定不存在的 URL，看 HTTP 状态码；在站长工具里看 404 列表及来源链接。

如何判断：不存在的页面应返回 404 或 410，而不是 200。把 404 用 301 或脚本整站跳到首页，容易被当成与首页重复的软 404，这在官方抓取说明里是需要避免的。自定义 404 页可以保留网站导航、说明原因，并提供搜索或重要入口。

怎么改：在服务器正确配置状态码和错误页。若某错误 URL 仍有外部链接，可 301 到真正对应的新页面，或修复来源链接；没有对应内容就保持 404/410。

### 导航、子域名与路径

文字导航、面包屑、当前栏目高亮，对用户和爬虫都更友好。页脚不要堆关键词链接。子域名会被当作相对独立的主机，没有明确产品线、地区站或体量需要时，优先用目录。绝对路径和相对路径都可以，关键是不要混用到产生重复或错误地址。无法做 301 时，内链写绝对的规范 URL 更安全。

## 五、页面级优化

### 标题：先求准确独特，不要死守字数线

要检查的是：每页 `<title>` 是否独特、是否准确描述本页、有没有全站套同一句或还在用「未命名文档」。

怎么查：用 Search Console 的 HTML / 网页体验相关提示，抽查源码，并搜索默认标题。

如何判断：Google 的[标题链接](https://developers.google.com/search/docs/appearance/title-link)可能来自 `<title>`、标题或页面中的显著文字，也常会改写。公开文档没有「中文必须 15～20 字、超过 25 或 30 就不合格」的规则。实践中仍建议把关键信息放在前部、避免堆砌和空话，但应以是否读得通、是否和本页一致为准，而不是卡一个固定字数。品牌名放在后面通常更合适，却不是法规。`noodp` 针对的开放目录早已停用，不必再加。

怎么改：首页、主要分类和重点产品页人工写标题；其余可用「内容名 - 分类 - 站点名」这类清晰模式生成，并保证翻页标题互不相同。

### 描述：为摘要准备一句人话，而不是为了「达标字数」

要检查的是：是否写了通顺、独特、与页面相符的 meta description，有没有和标题完全重复或只罗列关键词。

怎么查：抽查源码，并在搜索结果里看摘要是否来自这段描述。

如何判断：[摘要可能来自页面正文，也可能采用你写的描述](https://developers.google.com/search/docs/appearance/snippet)，搜索引擎会按查询改写。70 个中文字只是旧的展示经验，不是收录或排名门槛。写得差（堆词、重复标题、不成句）时，这段描述往往不会被用。

怎么改：小站和核心页人工写一两句能吸引点击的说明；大站可用正文首段或商品关键信息生成，但要避免全站重复。写不好可以先不写，把精力放在正文本身。

### 关键词 meta：可以不维护

Google 很早就公开说明[不会把 keywords 元标签用于排名](https://developers.google.com/search/blog/2009/09/google-does-not-use-keywords-meta-tag)。不必为它花时间；如果 CMS 允许，删掉也无妨。把精力放在可见的标题和正文上。

### 正文：自然覆盖主题，而不是数次数

要检查的是：正文是否围绕用户问题展开，重要主题是否出现在靠前、可读的位置，分类页有没有自己的说明文字。

怎么查：通读页面，而不是先跑密度工具。

如何判断：「短文出现 2～3 次、长文 4～6 次」「前 50～100 词必须出现」都是经验说法，不是官方公式。更应警惕的是关键词堆砌、正文短到被模板淹没，以及分类页只有列表、没有独特说明。同义词和相关表述有助于把主题写清楚，但不必为了分词去硬拆词组。

怎么改：按用户搜索意图重写，让标题、首段和正文一致。给分类页补上真正有用的导语。核心是写给人看。

### 标题层级、图片替代文字和代码体积

H1 用来标识本页的主标题，分类页用分类名、产品页用产品名，不要全站把网站名当成唯一的 H1。层级应跟文章结构走，不要整页滥用 H1/H2。Google 并没有把「全页只能有一个 H1」写成不可违反的排名条款，但一个清晰的主标题对人和系统都更友好。

图片的 `alt` 应简要描述图像内容；图片作为链接时，替代文字要能说明去向。Logo 的替代文字写成「站点名」或实际图形含义即可，不必为了「第一个链接」往里面塞首页目标关键词。

CSS 和 JS 外置、减少无意义嵌套、让主要内容在 DOM 中可被提取，这些仍有利于性能和渲染。旧资料里「HTML 小于 100KB、每页链接少于 100 个」的说法已经过时，现代引擎能处理更大的页面；今天应关注核心内容是否可访问，以及是否拖累 [页面体验](https://developers.google.com/search/docs/appearance/page-experience)，而不是守一条固定体积线。

### 页内锚文本，以及是否必须「导出外链」

正文里的内链应帮助读者到达相关内容，锚文本要具体、多样，避免全部完全匹配，也不要集中在页脚堆关键词。向维基百科式的正文引用学习即可。

适当链接到真正相关的高质量外部资料，对读者有用，也能把本页主题讲清楚。但「全站一条外链都没有就是不合格」并不是 Google 或 Bing 的公开标准。不要为了凑外链去链无关站点；有引用价值再自然写。

### 其他页面元素

W3C 校验通过与否对排名没有公开的直接权重，但严重到无法提取正文的 HTML 错误必须修。粗体、斜体按阅读需要使用，不要整段加粗堆词。有时效的内容按实际更新，更新是为了页面仍然正确，不是为了「招蜘蛛回访」而改无意义的日期。

## 收尾时可以这样验收

先确认 Search Console 和 Bing 里，核心页面没有大面积的抓取失败、误屏蔽或重复规范问题；再确认重要 URL 只有一个规范地址、404 是真 404、导航链接可抓取；最后抽查标题、H1 和正文是否一致、是否独特。

若某一项在工具里显示正常、但书中的旧「合格线」没达到，优先相信带原因的官方报告，而不是把经验百分比当成必须追上的指标。
